## 1. Архитектура и разделение слоёв

**Что сделано хорошо:**
- `main.py` — тонкая точка входа (~120 строк): делегирует выбор Python, проверку единственного экземпляра, установку зависимостей и запуск GUI, тяжёлые импорты (torch, faster-whisper) отложены до момента после проверки зависимостей.
- Более новые модули (`core/output_conflict.py`, `core/source_relocate.py`, `core/document_convert.py`, `postprocess/*`, `updates/*`) написаны как проверяемые функции без прямой зависимости от Tkinter — это правильный образец для остального кода.

**Проблемы:**
- ~~**`core/` фактически не отделён от Tkinter**~~ — **✅ Исправлено.** `core/queue_manager.py` и `core/input_files.py` больше не импортируют `tkinter`/`filedialog`/`messagebox`: диалоги выбора файлов/каталогов (`add_single_file`, `add_multiple_files`, `add_directory`) и диалог наблюдаемых папок (`open_watch_dirs_dialog`) перенесены в `ui/dialogs.py`, где им и место. `core/transcription.py` больше не вызывает `messagebox.askyesno` напрямую — подтверждение сохранения MP3 теперь идёт через duck-typed callback `app.ask_save_mp3_confirm(filename)`, реализованный в `ui/gui.py` (по образцу уже существовавшего `ask_overwrite` в `output_conflict.py`). Сам busy-wait (`while choice[0] is None: time.sleep(0.05)`) внутри `ask_save_mp3_confirm` **оставлен как есть** — это отдельная, не связанная с разделением слоёв проблема, см. раздел 2.
  Теперь очередь и логику добавления файлов можно тестировать без запущенного Tk mainloop; `ui/dialogs.py` остаётся единственным местом, которое реально показывает Tk-окна пользователю.

- ~~**`WhisperGUI` (`ui/gui.py`) — «божественный объект»**~~ — **✅ Частично исправлено.** Контракт `run_queue` / `save_files` зафиксирован в `core/host.py` (`Protocol TranscriptionHost`). `WhisperGUI` реализует его структурно (без наследования) и остаётся большим оркестратором. Тесты `tests/test_run_queue.py` / `tests/test_queue_controller.py` гоняют пайплайн против фейка без Tkinter. Распил `gui.py` не делался.

- **Настройки синхронизируются вручную в 4+ местах**: `settings.py: _DEFAULTS`, `WhisperGUI.__init__`, `WhisperGUI._persist_settings`, `ui/dialogs.py: show_ai_api_keys_dialog`. Добавление нового поля требует правки во всех четырёх местах без какой-либо проверки согласованности компилятором — уже сегодня это видно на примере legacy-пары `send_txt_to_ai`/`send_txt_to_cursor`, которую приходится синхронизировать вручную в нескольких файлах.

- **Много защитных `try/except ImportError` вокруг `from whisperfast.i18n import t`** (более 60 вхождений в `postprocess/providers/*` и `cursor_postprocess.py`) — рабочий, но явно скопипащенный паттерн, а не осознанное архитектурное решение; признак того, что граф зависимостей между модулями туже, чем хотелось бы.

## 2. Обработка ошибок и надёжность

**Что сделано хорошо:**
- Подпроцессы централизованы через `platform_util.py` (`run_logged_command`, `win_no_window_kwargs`) и переиспользуются во всех модулях, которые их вызывают.
- Файлы состояния (`log_store.py`, `single_instance.py`) пишутся через `.tmp` + `os.replace()` — правильный способ избежать повреждения JSON при аварийном завершении.

**Проблемы:**
- ~~**Избыточные обработчики исключений вида `except (X, Exception)`**~~ — **✅ Исправлено.** `whisperfast/utils.py` (`get_audio_duration_seconds`, `play_finish_sound`) и `whisperfast/ui/gui.py: _set_progress_value` теперь используют просто `except Exception`.

- **Активное ожидание (busy-wait) вместо нормальной синхронизации потоков** — **не исправлено, сознательно.** `core/output_conflict.py: ask_overwrite_via_tk` и новый `ui/gui.py: ask_save_mp3_confirm` (куда переехала логика подтверждения MP3 из `core/transcription.py`, см. раздел 1) по-прежнему ждут ответ Tk-диалога из фонового потока через `while ...: time.sleep(0.05)`. В `postprocess/common.py: copy_text_to_clipboard` для похожей задачи уже правильно используется `threading.Event` — этот приём стоит применить и здесь, но это отдельное изменение, которое пока не делалось.

- ~~**`WhisperModelSingleton` (`core/model_manager.py`) не защищён `threading.Lock`**~~ — **✅ Исправлено.** Добавлен `threading.RLock` (`_lock` — атрибут класса), и `get()`/`unload()`/`reset()` теперь выполняются внутри `with cls._lock:`, что убирает гонку между кнопкой «Обновить модель» и активной транскрибацией в другом потоке.

- Возвращаемые коды подпроцессов иногда не проверяются там, где ошибка проходит бесследно: `open_path.py` (строки 14, 16, 41, 43, 47) — если `xdg-open`/`open` не установлен, пользователь просто не получает файл без какой-либо обратной связи. Незначительная проблема UX, не риск падения.

## 3. Безопасность

Самое важное в этом разделе — два пункта про целостность автообновлений (ниже) и хранение ключей API.

- **Ключи API AI-провайдеров хранятся в `settings.json` в открытом виде** (`settings.py`, строки 29–36: `cursor_api_key`, `gemini_api_key`, `anthropic_api_key`, `azure_openai_api_key`; запись — простой `json.dump` в `ui/gui.py: _persist_settings`). Никакой интеграции с Windows Credential Manager/macOS Keychain нет. Любой процесс или человек с доступом к папке программы (или к её бэкапу) может прочитать все настроенные ключи открытым текстом.
  Хорошая новость: все четыре провайдера сначала проверяют переменные окружения и только потом `settings.json` — то есть пользователь может вообще не хранить ключ на диске, но диалог **[API keys]** в GUI активно предлагает именно вписать ключ в форму, которая сохранится в файл.
  **Частично исправлено:** после каждой записи `settings.json` теперь вызывается `_restrict_settings_file_permissions()` (`chmod 0600`). Это ограничивает доступ на POSIX-системах (Linux/macOS), но **ничего не даёт на Windows** — `os.chmod` там не меняет реальный ACL файла, а WhisperFastGUI — Windows-первое приложение (есть `install.bat`, нет установки под POSIX по умолчанию). Полноценное решение для Windows потребовало бы либо ACL через `pywin32`/`icacls`, либо переноса секретов в `keyring` (Windows Credential Manager) — это не сделано и остаётся открытым пунктом.
  Ключи ни разу не попадают в лог — это проверено отдельно и является плюсом.

- ~~**Самообновление программы не проверяет целостность скачанного кода**~~ — **✅ Исправлено для ZIP-пути.** Обновление берётся с GitHub Release (тег), не из `main.zip`; перед распаковкой обязателен SHA-256 (`SHA256SUMS`), опционно GPG, если в `resources/release_signing_key.asc` есть ключ. Zip-slip и `_apply_update.py` без интерполяции имён в `.bat` остаются. FFmpeg/Pandoc по-прежнему без checksum.

- **Тот же класс риска — для автозагрузки FFmpeg/Pandoc** (`setup/external_tools.py: _download_url`, `_install_via_github_zip`): бинарники скачиваются с GitHub Releases и распаковываются без проверки контрольной суммы перед тем, как они начинают вызываться через `subprocess`.

- **Одно использование `shell=True`**: `open_path.py:73` (`subprocess.Popen(f'explorer /select,"{path}"', shell=True)`) — запасной путь, срабатывающий только если `ShellExecuteW` не сработал. Путь — локально выбранный пользователем файл, поэтому практическая эксплуатируемость низкая, но сам паттерн (интерполяция строки в `shell=True`) обычно избегается; безопасная list-форма вызова есть строкой выше в той же функции.

- Не найдено использования `eval`/`exec`/`pickle`/`marshal` — небезопасной десериализации в проекте нет.

- Транскрипты (потенциально чувствительная речь) сохраняются без шифрования в `app_log.json` (превью до 3 сегментов на файл, до 60 дней хранения) — ожидаемо для функциональности «посмотреть прошлые сессии», но стоит иметь в виду при использовании программы для конфиденциальных записей (медицина, юриспруденция, HR).

- ~~**Существенное дублирование между четырьмя AI-провайдерами**~~ — **✅ Исправлено.** Общий цикл «проверка ключа → цепочка промптов через API либо буфер обмена + браузер» вынесен в `postprocess/providers/base.py` (`run_provider_chain()`, `run_browser_fallback()`); `claude.py`, `gemini.py`, `copilot.py` теперь вызывают эти общие функции вместо дублирования ~90-строчной логики каждый. - Не найдено ни одного голого `except:` и ни одного оставленного `TODO`/`FIXME` — признак активно поддерживаемого, а не заброшенного кода.

## 7. Зависимости и упаковка

## 8. Логирование

Проект не использует стандартный модуль `logging` — вместо этого написана собственная, GUI-интегрированная система (`log_store.py` + `log_panel.py`) с группировкой по дням, ленивой подгрузкой и кликабельными путями. Это осознанный дизайн ради богатого интерактивного лога, а не недосмотр. Обратная сторона: нет уровней логирования (`DEBUG`/`INFO`/`WARNING`), фильтрация невозможна, а сторонние библиотеки (torch, faster-whisper) никак не перехватываются этой системой. Единственный переключатель детализации — проверка `os.environ.get("DEBUG")` в одном месте (`transcription.py:347`).

Ретенция уже реализована разумно: `MAX_DAYS = 60`, `MAX_ENTRIES_PER_DAY = 2000`, `MAX_SEGMENT_PREVIEWS = 3` — но не по объёму диска, только по количеству.

### 11.2 Новые находки — надёжность

- ~~🆕 **Отсутствие валидации типов полей `settings.json`**~~ — **✅ Исправлено.** `load_app_settings()` сверяет типы с `_DEFAULTS` и откатывает битые поля (например `"output_mode": 123`) к дефолту, не роняя старт.
- ~~🆕 **Молчаливый сбой парсинга версии из README.md**~~ — **✅ Исправлено.** Неудачный парсинг логируется; `_version_is_newer` / `check_app_update` не предлагают обновление, если локальная версия `"unknown"`.
- 🆕 **`i18n/lang_manager.py: t()` перехватывает только `KeyError` вокруг `.format(**kwargs)`**, хотя реальные опечатки в `lang.json` (позиционный `{0}` вместо именованного, незакрытая скобка, неверный format-spec) кидают `IndexError`/`ValueError`, которые ничем не пойманы. Отдельный fallback-путь в `i18n/fallback.py` перехватывает шире (`KeyError, ValueError`) — «резервный» механизм внутренне надёжнее «основного», стоит унифицировать.
- 🆕 **`core/output_conflict.py: ask_overwrite_via_tk` — реальная (хоть и ленивая) зависимость `core/` → `ui/`.** Функция строит Tk-диалог прямо в `core/` (это и раньше было задокументировано как единственное осознанное исключение), но дополнительно лениво импортирует `from whisperfast.ui.dialogs import center_toplevel` для центрирования окна. Рабочее, но не полностью независимое от `ui/` — при добавлении встречного модульного импорта в `ui/dialogs.py` это создаст циклическую зависимость. Не регресс от недавних правок (файл не трогали), просто ранее эта конкретная деталь не была явно зафиксирована.
